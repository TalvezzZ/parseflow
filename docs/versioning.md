# ParseFlow 版本策略

状态：生效（2026-11-24）。本文约束版本号如何确定，不约束发布时机；发布门禁见 [operations.md](operations.md) 与各版本方案。

## 1. 三段式含义

```text
MAJOR.MINOR.PATCH
```

| 段 | 含义 | 典型触发 |
|---|---|---|
| MAJOR | 破坏既有契约 | 删除/改名公开端点、改变既有字段语义、改变 MCP 工具签名、不兼容的数据迁移 |
| MINOR | 新增对外可感知的能力，且向后兼容 | 新增输出格式、新增端点、新增可选 Provider 或配置值、新增独立能力面 |
| PATCH | 无新增对外能力 | 内部重构、性能优化、缺陷修复、向后兼容的附加字段、文档与测试、依赖升级 |

## 2. 判定边界

以下判定容易出错，明确如下：

| 变更 | 判定 | 说明 |
|---|---|---|
| 响应/结果中新增可选字段 | **PATCH** | 向后兼容，不改变既有字段语义；不为加字段升 MINOR |
| 结果 schema 增加版本号字段 | **PATCH** | 只要旧数据仍按旧版本读取 |
| 内部模块拆分、接口下沉、渲染层解耦 | **PATCH** | 对外行为不变即 PATCH，哪怕改动量很大 |
| 新增一种可导出格式 | **MINOR** | 对外可感知的新能力 |
| 新增一种可选输入格式 | **MINOR** | 同上 |
| 新增可选 Provider / 新增 `*_PROVIDER` 取值 | **MINOR** | 用户可感知的选择面扩大 |
| 改变默认 Provider / 默认解析链路 | **MAJOR 级变更** | 即使接口不变，默认行为改变也按破坏性对待，需评审与回滚开关 |
| 仅改内部实现但输出字节有差异 | **PATCH + 记录** | 必须在方案中列出差异样例与原因 |

原则：**改动量大不等于版本号大。** 版本号表达的是"对外契约变了多少"，不是"工作量多大"。

## 3. 发版节奏约束

1. **不为单个内部阶段发版。** 内部阶段可以合并到一个 PATCH 或 MINOR 内交付，方案里分阶段记录即可。
2. **MINOR 必须有对外可感知的新能力。** 没有新能力就不升 MINOR。
3. **同一交付物不拆成多个 MINOR。** 共享同一依赖、同一 extra、同一验收面的工作，放在同一个版本里。
4. **PATCH 可随修随发**，不要求攒批。
5. **未发布版本不预支编号。** 当前基线尚未发布时，不为后续计划预留多个 MINOR 编号。

## 4. 历史复盘（1.1.0–1.6.0）

按上述规则回看，以下版本号偏大，仅作校准，不回改历史：

| 版本 | 实际内容 | 按本策略应为 |
|---|---|---|
| `1.1.0` | 事件时间线、结构化日志、Prometheus、ready 诊断 | PATCH（可观测性，无新能力面） |
| `1.3.1` | OCR 页面预览 | PATCH（已正确） |
| `1.4.0` | 删除联动清理、孤儿回收、路径去除、校对补完 | PATCH（治理与修复） |
| `1.5.0` | 供应链、单进程锁、优雅关闭、容量验证 | PATCH（可靠性） |
| `1.6.0` | 统一文件结果存储、Excel 完整坐标 | MINOR（结果契约与坐标能力变化，保留） |

结论：把"工程治理"与"可靠性"类工作当作 MINOR 是版本通胀的主要来源，后续一律按 PATCH 处理。

## 5. 一致性要求

版本号变更必须同步：`pyproject.toml`、`app/version.py`、OpenAPI 元数据、README 工作版本说明、`docs/roadmap.md`、对应 `docs/plan-<version>.md`、镜像标签与 Git Tag。版本号更新不替代发布门禁。
