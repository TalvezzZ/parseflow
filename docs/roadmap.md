# ParseFlow 版本路线图

## 1. 当前基线

最后记录的稳定标签为 `v1.4.0`；当前工作版本为 `1.6.0`，统一结果文件存储已完成本地实现和验证，尚未创建新的Tag、Release或发布镜像。既有基线已具备：

- PDF、DOCX、Excel、PowerPoint、RTF、HTML、XML、CSV/TSV、图片、音视频预处理。
- 扫描 PDF 和独立图片的本地 PaddleOCR，并输出页面预览与文本坐标。
- 旧版 Office 通过 LibreOffice 转换后解析。
- 文件上传、异步任务、规则规划、REST API 和 MCP。
- React/Vite 解析工作台，含任务中心、筛选、深链接与 OCR 校对视图。
- 前后端、LibreOffice、FFmpeg 和 OCR 的单容器 Docker 部署。
- 本地 stdio MCP 与带 API Key 的远程 Streamable HTTP MCP。

`v1.2.0` 完成了质量报告、Provider provenance 和安全结果导出；`v1.3.0` 完成了工作台体验、可访问性与真实浏览器 E2E；`v1.3.1` 补充了 OCR 页面预览发布；`v1.4.0` 完成了存储生命周期治理与 OCR 校对补完。`v1.5.0` 已启动，目标是供应链与发布自动化、任务生命周期可靠性和容量验证。

基线之上已确定下一阶段方向：`v1.6.1`（PATCH）先做渲染层解耦，`v1.7.0`（MINOR）再引入富格式导出与可选解析引擎。版本号判定规则见 [版本策略](versioning.md)；该方向的取舍依据、吸收清单与不吸收项见 [DocVortex 能力吸收决策记录](docvortex-adoption.md)。

## 2. 产品演进原则

```text
先完成解析能力与结果展示的一致性；
再把公开入口收敛为“文件流 + 不透明 ID + 异步任务”；
使用本地文件持久化任务和结果；
随后完成安全、部署、浏览器测试与可观测性；
最后冻结 API、MCP 和数据契约并发布 1.0.0。
```

每一版本均应满足：

- 不将未实现能力伪装为成功结果。
- 公开接口不暴露服务器真实路径。
- 结果保留实际 Provider、计划、警告、质量指标和 provenance。
- 新能力有自动化测试和真实运行验证。
- 版本号、文档、API、MCP 和镜像标签保持一致。

## 5. 已确认的架构决策

### 5.1 公开入口只接受文件流和 ID

公开 REST API 与远程 HTTP MCP 不允许调用方提交：

```text
path
output_dir
```

服务端负责保存上传文件、分配输入路径和 artifact 目录。客户端只持有：

```text
file_id
task_id
artifact_id
```

### 5.2 解析统一异步执行

```text
上传文件流 → 返回 task_id → queued → planning → running
                                   → succeeded | partial | failed | cancelled | interrupted
```

客户端通过任务 API 或 MCP 查询状态，不依赖长连接等待解析完成。

### 5.3 暂停 callback

在目标校验、出站网络策略、签名、重试和审计方案明确前，不对外提供 callback。`0.8.0` 将从公开请求和 MCP 工具中移除该参数。

### 5.4 本地文件持久化

首个持久化版本不引入数据库和 Redis，采用：

```text
data/files/{file_id}/...
data/tasks/{task_id}.json
data/artifacts/{task_id}/...
```

使用原子写入、文件锁、schema version、启动恢复、TTL 和容量限制。后续是否迁移数据库由实际规模决定。

`1.6.0`继续保留任务JSON仓库，不为结果路径登记新增SQL数据库。完整结果由任务artifact目录中的文件承载：`result/manifest.json`、`result/document.json`及按单元分块数据；任务记录只保存状态、统计、相对引用与有界预览。Excel独立使用 `workbook/manifest.json` schema 2及每Sheet gzip块，旧SQLite结果保留读取兼容。文件先原子发布，再发布任务引用；任务列表不加载完整结果。路径登记是可迁移契约，不等同于本轮已经引入数据库或对象存储。

### 5.5 默认本机部署

在多用户身份和文件权限模型完成前，ParseFlow 定位为本机或可信内网服务。Docker 默认绑定 `127.0.0.1`，公网监听必须显式开启并置于受支持的认证代理之后。

### 5.6 解析与渲染分层，引擎可替换

`1.6.1` 起把"结果表示生成"从 Skill 中移出，形成三层：

```text
解析（Skill/Provider） → DocumentResult（可序列化枢纽） → render（内存产物） → export（落盘/预算/原子发布）
```

约束：

- 渲染器只读 `DocumentResult`，不持有 Skill、Provider 或文件句柄；新增输出格式只加渲染器，不改解析代码。
- 渲染不写磁盘，导出不排版；字节预算、暂存目录、原子发布、可杀 worker 全部留在导出层。
- 引擎可替换：外部解析/渲染引擎只能以 Provider 或 optional extra 形式接入，不进入主依赖、不改默认值。
- 默认解析链路变更必须由基准数据驱动，且保留回滚开关；不得以对标外部项目跑分为由调整默认值。
- 协议纪律：仅重构不改协议不升版本；改变 `pages`/`blocks`/`tables` 字段语义必须升 `schema_version` 并留迁移说明。
- 不引入的能力：外部引擎的 OCR 外包策略、高频破坏性迭代节奏、重依赖进主依赖。

详见 [DocVortex 能力吸收决策记录](docvortex-adoption.md)。

## 7. 暂不纳入 1.0 前置范围

以下能力不阻塞 `1.0.0`：

- 多用户/多租户权限系统。
- PostgreSQL/Redis 分布式任务。
- 对象存储和分布式 Worker。
- ASR、摘要、语义切块、标签和知识索引。

这些能力应在基础契约稳定后按实际业务需求单独立项。

## 8. 已确认的暂缓决策

以下事项已有明确结论，不作为缺口重复立项：

### 8.1 LLM 规划能力暂缓启用

`app/agent/factory.py` 的 `create_parse_agent()` 与 `langchain` / `langchain-openai`
依赖予以保留，但当前**没有任何调用方**，默认链路仍是 `v0.6.0` 的规则规划器
（`RuleBasedPlanner`），无需模型 API Key 即可完成解析。

保留原因：后续可能作为可选规划后端接入，用于处理规则难以覆盖的目标（如
`goal` 的语义理解与多步解析编排）。启用前需要先明确：模型配置缺失时的降级
路径、失败与重试语义、以及是否影响已冻结的 v1 契约。

在此之前，该模块属于"有边界、未接线"的预留能力，不计入功能缺口。

### 8.2 其他预留但未接线的边界

- `app/skills/pdf/adapters/mineru.py`：MinerU Provider 边界已定义，但未在
  `create_default_registry()` 中注册，也没有 runner 注入路径与测试。
- `app/skills/media/asr.py`：ASR Provider 仅有 Protocol 与数据模型，无实现；
  当前工作区视频阶段可提取已有文本字幕和时间轴、按需准备音轨；仍如实返回“未执行ASR”的警告，不把字幕提取计为语音转写。实施见 [视频第一阶段方案](video-parsing-phase1.md)。

两者都需要真实可用的本地模型与验证手段后才启用，启用前不宣称能力可用。
