# ParseFlow v1.8.0 技术方案：格式覆盖、公开契约与分发（按需立项）

状态：方案草案，**未排期**。仅在 v1.7.0 完成且出现明确业务需求时启动。依据见 [DocVortex 能力吸收决策记录](docvortex-adoption.md)。

版本定位：预留的 **MINOR** 编号，不预支、不承诺。三项事项相互独立，启动时可拆分为独立小版本，届时再定编号。

## 目标与边界

- 输入格式扩展：OFD、EPUB、ODT/ODS/ODP、MHTML/MHT；每项独立立项、独立验收，不打包承诺。
- 公开接口冻结：为 `Provider` / `Skill` 建立静态清单与签名契约测试。
- 分发：明确继续 Docker-only，还是提供平台 wheel；不承诺未验证的平台。
- 不改变既有格式行为；新格式必须走同一套任务、存储、预算与导出链路。

## 格式覆盖

- 每新增一种格式：扩展 `FILE_ALLOWED_SUFFIXES`、能力声明、规划规则、预算与测试夹具。
- 优先顺序按业务价值：OFD（政企版式文档）> EPUB > ODF > MHTML。
- 实现路径二选一并在方案中写明：借外部 analyzer 适配，或自研 Provider；两者都必须产出统一 `DocumentResult`。
- 未实现或不可用时如实返回不支持，不落空结果。

## 公开契约冻结

- 新增 `app/skills/public_api.py`：静态登记公开模块、符号与类方法签名，作为对外契约清单。
- 新增 `tests/test_public_api.py`：校验清单内符号可导入、`__all__` 完整、签名未漂移；新增跨模块依赖必须同步更新清单与文档。
- 与既有 `schemas/*.json` 快照形成"结构 + 符号"双重门禁。

## 分发

- 若提供 wheel：声明平台矩阵（Linux glibc 版本、Windows 架构、macOS 架构），只发布构建验证过的平台；不发布 sdist 时须在文档中说明源码安装路径。
- 若维持 Docker-only：在 README 与操作手册中明确这一承诺，不宣称 pip 直装可用。
- 两种选择都不改变运行时行为。

## 执行顺序

1. 按业务需求选定首个格式并独立立项。
2. 落 `public_api.py` 与契约测试（可与格式工作并行）。
3. 分发决策与平台矩阵文档。
4. 逐格式验收与文档同步。

## 验收

- 每种新格式：上传、规划、解析、存储、导出、清理全链路可用，且有失败路径测试。
- 契约测试能在签名漂移时失败，并在正常重构时保持通过。
- 分发承诺与实际构建产物一致，文档不含未验证的平台声明。
- 后端全量测试、前端单测与构建通过。
